## Final plan: Game Voting App

### Architecture

```
Browser (React SPA) ──/api──▶ nginx ──▶ PHP-FPM (Slim 4) ──▶ EOA REST API
                                              │              (games, vote counts)
                                              ▼
```

- **Their API** stores games and vote counts, and the game list is read from it.
- **MySQL** stores who each user is, who voted for what, who added each game, the daily limit, and normalized titles for duplicate checks.
- **The API key** is kept on the server in `.env` and is never sent to the browser.
- **Write order:** check the rules in the database, call the API, then save to the database. If the API call fails, nothing is saved locally and the user sees an error. If the database save fails after the API succeeded, the API change is undone.

### Business rules

1. **Identity:** the backend sets an anonymous UUID in an httpOnly cookie, backed by a `users` row. If someone clears their cookies, the app treats them as a new user. The README will document this as an accepted limitation.
2. **Local day:** the browser sends its time zone on the first visit. That zone is saved with the user and used from then on.
3. **One action per day:** voting or adding a game uses the day's action. A unique `(user_id, local_date)` index enforces this even with simultaneous requests.
4. **Voting:** one vote per user per game, as a toggle.
5. **Removing a vote:** this never needs an action. Removing a vote cast today gives today's action back. Removing an older vote gives nothing back.
6. **Removing a game:**
   - Only the person who added the game can remove it. Other users don't see the button, and the backend returns 403 if they try.
   - Removing a game you added today gives today's action back, the same undo rule as votes.
   - If other users voted for that game *today*, their action is given back, since they lost it through no fault of their own. Older votes are just deleted.
   - Games that exist in the API but not in our database (for example, ones added through the docs' "Try it" form) are shown but can't be removed by anyone.
7. **Limit status in the UI:** a banner shows whether today's action is available or used, plus when it resets at midnight local time.

### Duplicate titles

- **Normalization:** titles are trimmed, inner whitespace is collapsed to single spaces, and the result is lowercased.
- **Enforcement:** a unique index on the normalized title. The backend reserves the row, calls `/games/add`, then saves the API's ID. If the API call fails, the reservation is removed.

### Database schema (draft)

- `users`: id (UUID), timezone, created_at
- `games`: id, api_id (unique), title, title_normalized (unique), created_by → users, created_at
- `votes`: user_id, game_id, cast_local_date, created_at, with primary key (user_id, game_id)
- `daily_actions`: user_id, local_date, type (vote/add), ref_id, with unique (user_id, local_date)

### Backend API (our endpoints)

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/me` | Today's limit status and the user's time zone |
| GET | `/api/games` | Games sorted by votes, each with `votedByMe` and `canRemove` |
| POST | `/api/games` | Add a game (uses the daily action) |
| DELETE | `/api/games/{id}` | Remove a game (creator only) |
| POST | `/api/games/{id}/vote` | Vote (uses the daily action) |
| DELETE | `/api/games/{id}/vote` | Remove the user's vote |

- **Errors:** every error is returned as `{ error: { code, message } }`, with codes such as `DUPLICATE_TITLE`, `DAILY_LIMIT_REACHED`, `NOT_OWNER` and `UPSTREAM_UNAVAILABLE`.
- **Upstream failures:** problems with their API come back as 502 or 503 with a friendly message, never as raw errors.

## Findings

### High
**1. PHP is running with no `php.ini`.** I checked this live: `display_errors=1`, `log_errors=0`, `expose_php=1`.
- **Effect:** any PHP warning gets printed into the API response, which corrupts the JSON and exposes file paths. It also isn't logged anywhere. Every response carries `X-Powered-By: PHP/8.3.36`.
- **Fix:** start from PHP's production `php.ini` in the Dockerfile and add our own overrides.

### Medium
**2. Write endpoints accept any body format, with no CSRF defense beyond SameSite.** A plain form-encoded POST created a game during my check (I cleaned it up afterwards). XML bodies are parsed too.
- **Why it matters:** `SameSite=Lax` stops cross-site requests, but not requests from other subdomains of the same site, or browsers that ignore SameSite.
- **Fix:**
  - Require `application/json` on `POST /api/games`.
  - Require a custom header such as `X-Requested-With` on every write. Browsers have to ask permission before sending a custom header cross-site, which blocks forged requests.
  - Reject requests whose `Origin` doesn't match ours.

**3. Missing response headers.**
- **What's missing:** none of `X-Content-Type-Options: nosniff`, `Referrer-Policy`, frame protection or a CSP are sent. The API doesn't send `Cache-Control: no-store`, even though its responses are per-user. nginx shows its version (`Server: nginx/1.27.5`).
- **Fix:** add the headers in nginx and turn off `server_tokens`.

**4. A user row is created on every visit without a cookie, including plain reads.** My three test requests created three rows. Crawlers, link previews and monitoring tools would fill the table without limit.
- **Fix:** create the user on their first write instead. Reads without a cookie get a guest view. The time zone is still locked from the first action, so it can't be gamed.

**5. No rate limiting.** Clearing the cookie gives a new identity. The brief accepts that for anonymous users, but a script could still flood the shared upstream library.
- **Fix:** an nginx per-IP limit on `/api` writes, and a note in the README.

**6. Duplicate check misses Unicode variants.** `é` can be stored as one character or as `e` plus an accent mark. The two look identical but count as different titles, so "Pokémon" can be added twice.
- **Fix:** add the PHP `intl` extension and normalize titles with NFKC before comparing.

### Low
**7.** The identity cookie has no `Secure` flag. Set it whenever the request came in over HTTPS.

**8.** The PHP image ships PHPUnit and the tests. Add a production build target that installs without dev dependencies.

**9.** `composer.json` doesn't declare the PHP extensions the code needs (`mbstring`, `pdo_mysql`, and `intl` after fix 6).

**10.** There's an edge case in `VoteService::restoreVote`. If the game is deleted while a vote removal is being rolled back, the database insert fails and the user gets a 500 instead of the friendly 502. Catch that error and log it.

**11.** nginx allows request bodies up to its 1 MB default. Lower that to 16 KB for `/api`.

**12.** The 429 daily-limit response has no `Retry-After` header. Add one with the seconds until the user's local midnight.

### Best practices
**13. No CI.**
- **Fix:** add a GitHub Actions workflow that runs PHPUnit against a MySQL service, Vitest and the build, plus a secret scan with gitleaks.
- **Why:** the local pre-commit hook can be skipped with `--no-verify`, or by cloning without running `setup-hooks.sh`.

**14. No static analysis for PHP.**
- **Fix:** add PHPStan at level 8 and a PSR-12 style check. The frontend already has oxlint.

**15. The concurrency test gap is still open.** I'd keep it documented rather than add a forking test.
