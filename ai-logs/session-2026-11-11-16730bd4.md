## Final plan: Game Voting App

### Architecture

```
Browser (React SPA) ──/api──▶ nginx ──▶ PHP-FPM (Slim 4) ──▶ EOA REST API
                                              │              (games, vote counts)
                                              ▼

```

- **Their API** stores games and vote counts, and the game list is read from it.
- **MySQL** stores who each user is, who voted for what, who added each game, the daily limit, and normalized titles for duplicate checks.
- **The API key** is kept on the server in `.env` and is never sent to the browser.
- **Write order:** check the rules in the database, call the API, then save to the database. If the API call fails, nothing is saved locally and the user sees an error. If the database save fails after the API succeeded, the API change is undone.

### Business rules

1. **Identity:** the backend sets an anonymous UUID in an httpOnly cookie, backed by a `users` row. If someone clears their cookies, the app treats them as a new user. The README will document this as an accepted limitation.
2. **Local day:** the browser sends its time zone on the first visit. That zone is saved with the user and used from then on.
3. **One action per day:** voting or adding a game uses the day's action. A unique `(user_id, local_date)` index enforces this even with simultaneous requests.
4. **Voting:** one vote per user per game, as a toggle.
5. **Removing a vote:** this never needs an action. Removing a vote cast today gives today's action back. Removing an older vote gives nothing back.
6. **Removing a game:**
   - Only the person who added the game can remove it. Other users don't see the button, and the backend returns 403 if they try.
   - Removing a game you added today gives today's action back, the same undo rule as votes.
   - If other users voted for that game *today*, their action is given back, since they lost it through no fault of their own. Older votes are just deleted.
   - Games that exist in the API but not in our database (for example, ones added through the docs' "Try it" form) are shown but can't be removed by anyone.
7. **Limit status in the UI:** a banner shows whether today's action is available or used, plus when it resets at midnight local time.

### Duplicate titles

- **Normalization:** titles are trimmed, inner whitespace is collapsed to single spaces, and the result is lowercased.
- **Enforcement:** a unique index on the normalized title. The backend reserves the row, calls `/games/add`, then saves the API's ID. If the API call fails, the reservation is removed.

### Database schema (draft)

- `users`: id (UUID), timezone, created_at
- `games`: id, api_id (unique), title, title_normalized (unique), created_by → users, created_at
- `votes`: user_id, game_id, cast_local_date, created_at, with primary key (user_id, game_id)
- `daily_actions`: user_id, local_date, type (vote/add), ref_id, with unique (user_id, local_date)

### Backend API (our endpoints)

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/me` | Today's limit status and the user's time zone |
| GET | `/api/games` | Games sorted by votes, each with `votedByMe` and `canRemove` |
| POST | `/api/games` | Add a game (uses the daily action) |
| DELETE | `/api/games/{id}` | Remove a game (creator only) |
| POST | `/api/games/{id}/vote` | Vote (uses the daily action) |
| DELETE | `/api/games/{id}/vote` | Remove the user's vote |

- **Errors:** every error is returned as `{ error: { code, message } }`, with codes such as `DUPLICATE_TITLE`, `DAILY_LIMIT_REACHED`, `NOT_OWNER` and `UPSTREAM_UNAVAILABLE`.
- **Upstream failures:** problems with their API come back as 502 or 503 with a friendly message, never as raw errors.
